# ANP 참고와 벤치마크 동기화

이 문서는 Agent Chat Desktop의 벤치마크 결과 동기화가 [Agent Network Protocol(ANP)](https://github.com/agent-network-protocol/AgentNetworkProtocol)를 어디까지 참고했는지와, 향후 호환을 확장할 때의 기준을 기록합니다. 현재 구현은 **ANP 구현체나 ANP 호환 프로토콜이 아닙니다**.

## ANP의 기본 개념

ANP는 에이전트가 웹 위에서 서로를 식별하고, 찾고, 기능을 설명하고, 안전하게 통신·협업하기 위한 프로토콜 묶음입니다. 기존 HTTP·DNS·TLS 같은 웹 기반을 다시 만들기보다는 그 위에 에이전트용 계층을 추가하는 방향입니다.

| 영역 | ANP에서 다루는 역할 | 동기화 기능과의 관련성 |
|---|---|---|
| 신원 | `did:wba`를 포함한 DID 기반 신원과 인증 | 현재의 로컬 장치 ID·일회용 코드보다 강한 장치 신원으로 확장할 수 있음 |
| 이름 | WNS 핸들로 사람이 읽을 수 있는 에이전트 이름을 DID에 연결 | 현재는 사용자가 PC 주소를 직접 전달함 |
| 설명 | Agent Description으로 기능·접속점·인터페이스를 게시 | 어떤 종류의 데이터를 동기화할 수 있는지 선언하는 기반이 될 수 있음 |
| 발견 | `.well-known` 등의 능동 발견과 등록 기반의 수동 발견 | 현재의 수동 주소 입력을 안전한 장치 검색으로 바꿀 수 있음 |
| 메시징·객체 전송 | 직접 메시지, 종단 간 암호화, 첨부·대용량 객체 전송 | 결과 전송을 암호화된 표준 메시지·객체 전송으로 바꿀 수 있음 |
| 협상 | 후속 인터페이스·스키마·보안 프로필을 고르는 메타 프로토콜 | 동기화 버전과 전송 가능 데이터 형식을 상호 합의하는 데 활용 가능 |

ANP 저장소 기준으로 `did:wba`, Agent Description, Agent Discovery, 종단 간 메시징 계열은 1.1 문서군에 포함되어 있고, 메타 프로토콜은 아직 초안입니다. 따라서 향후 도입 시에도 초안과 출시된 사양을 구분해 선택합니다.

## 현재 구현에서 참고한 원칙

이번 동기화는 ANP의 형식이나 DID를 사용하지 않지만, 다음 설계 원칙을 작게 적용했습니다.

1. **명시적 연결**: 상대 PC 주소와 일회용 코드를 사용하며, 상대 PC의 사용자가 연결 요청을 직접 승인해야 합니다.
2. **장치 단위 신뢰 관계**: 승인된 각 PC에 독립 인증 토큰을 만들고, 토큰은 소유자 전용 로컬 설정 파일에만 보관합니다.
3. **명확한 기능 범위**: 완료된 벤치마크 원본 기록만 전송하며 API 키, 연결 인증 정보, 대화, 활동 로그는 전송하지 않습니다.
4. **버전 있는 구조화 전송**: `/agent-chat/benchmark-sync/v1` 아래의 JSON 요청·응답으로 페어링과 결과 전송을 구분합니다.
5. **재전송 안전성**: 원본 장치 ID·원본 벤치마크 ID와 결과 지문을 사용해 순환 동기화의 중복을 막고, 내용이 다른 동일 원본은 충돌로 남깁니다.

## 현재 범위와 보안 한계

현재 기능은 신뢰하는 같은 네트워크에서 결과를 직접 교환하는 용도입니다. 장치 인증 토큰은 있지만 TLS나 ANP의 DID 기반 인증·종단 간 암호화는 아직 적용하지 않았습니다. 따라서 공용 Wi‑Fi, 인터넷에 노출된 주소, 신뢰할 수 없는 네트워크에서는 사용하면 안 됩니다.

자동 장치 발견, 백그라운드 동기화, 사람 친화적 장치 이름의 전역 해석, 대화·첨부 파일 동기화도 현재 범위에 넣지 않았습니다.

## ANP를 활용한 다음 확장 방향

1. **DID 기반 장치 신원**: 임의의 로컬 장치 ID와 일회용 코드 대신 `did:wba` 신원·서명으로 상대 장치를 확인합니다.
2. **Agent Description 게시**: 동기화 가능 데이터, 버전, 크기 제한, 보안 요구 사항을 Agent Description으로 게시합니다.
3. **발견 도입**: 사용자가 주소를 직접 옮기지 않아도, 같은 조직 또는 허용된 범위에서 Agent Discovery로 후보를 찾습니다.
4. **암호화된 전송**: TLS와 ANP 메시징의 종단 간 암호화 프로필을 검토해 전송 내용·인증 정보를 보호합니다.
5. **기능 협상**: 메타 프로토콜이 안정화되면 `benchmark-result` 전송 인터페이스와 스키마 버전을 협상하도록 검토합니다.

이 단계들은 ANP의 출시 상태, Go 생태계의 지원 수준, 사용자 경험과 보안 검토를 거친 뒤 별도 작업으로 도입합니다.
