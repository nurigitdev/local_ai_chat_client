# Decision Benchmark 기능 추가 구현 계획서

작성일: 2026-10-13

상태: GUI 1차 구현 · 서버 실행·채점 미연결, 기본 데이터셋 문항 선정 필요

## GUI 1차 구현 현황

2026-10-13 기준 모델 실험실에 `생성형 평가 / Decision Benchmark` 선택과 Decision의 실험 설정·테스트셋·결과 비교 화면을 추가했다.

- 서버·모델·환경 입력, 평가 대상 선택·추가·삭제, 세 평가 유형과 한국어·영어·둘 다 선택을 제공한다.
- 세 유형 모두 한국어·영어 대응 예제를 제공한다. 총 12문항이며 한국어 기본 선택은 6문항이다. 화면 검증용 예제이며 정식 기본 벤치마크 데이터는 아니다.
- 예제를 사용자 세트로 복제해 과제·기준·문항·정답을 편집하고 대응 문항을 추가할 수 있다.
- JSON 테스트셋 가져오기·내보내기, CSV 문항 내보내기, 설정 초안의 웹뷰 로컬 저장을 제공한다. API 키는 저장하지 않는다. 데스크톱 내보내기는 저장 대화상자와 JSON·CSV 전용 Go 파일 저장 명령을 사용한다.
- 유형별 System One 요청 미리보기와 입력 형식 검증을 제공한다. 서버 연결 검사와 실행·채점·결과 저장·보고서 기능은 아직 연결하지 않았으며, 관련 버튼은 비활성화하고 준비 상태를 표시한다.
- 결과 화면은 실제 실행 기록이 없는 빈 상태를 제공한다. 예제 성능 수치를 실제 결과처럼 표시하지 않는다.

첫 GUI의 데이터 타입과 JSON v1은 프런트엔드 설정 초안용이다. 이후 백엔드의 버전·출처·리비전·채점 메타데이터 계약을 추가할 때 기존 사용자 초안의 호환 또는 변환 경로를 마련한다. CSV 가져오기는 후속 구현 항목이다.

## 1. 목적과 합의 사항

여러 의사 결정 모델에 같은 입력과 판단 기준을 제공하고, 정답이 있는 데이터셋으로 판단 품질·확률 품질·처리 시간을 비교한다. 특정 모델의 데모를 넘어, 모델별로 어떤 판단 과제에 강하거나 약한지 확인하는 것이 목적이다.

| 항목 | 합의 내용 |
|---|---|
| 기능 이름과 위치 | 기존 모델 실험실 안에 별도 평가 종류인 **Decision Benchmark**를 추가한다. |
| 모델 범위 | 첫 버전은 System One/Jev 호환 HTTP 서버로 제공되는 모델을 지원한다. |
| 초기 연결 대상 | DGX Spark의 Laya Multilingual과 Ollama에서 실행하는 Nimble 등 Decision 모델 |
| 평가 종류 | 기본 세트에 선택형 분류 `choice`, 예/아니오 판단 `noul`, 등급 평가 `score`를 모두 포함한다. 각 유형의 실제 문항·정답은 선정·검토한다. |
| 기본 언어 | 한국어. 영어 대응 세트도 제공하고 한국어·영어·둘 다 실행을 선택한다. |
| 데이터셋 운영 | 기본 제공 세트와 사용자가 편집·가져온 세트를 모두 지원한다. |
| 결과 활용 | 실행 기록 저장, 최대 3개 기록 비교, Markdown/HTML 보고서 내보내기·가져오기 |

Qwen 추론 강도 선택은 대화 중의 예시였으며 이 기능의 실제 사용 목적이 아니다. 앱의 요청 라우팅, 추론 강도 자동 조절, 운영 정책 적용은 이번 기능에 포함하지 않는다. 사용자가 직접 정답 데이터 100~300개를 만들어야 시작할 수 있다는 조건도 두지 않는다.

Hugging Face 모델 다운로드·설치·추론 서버 운영과 System One 비호환 모델의 어댑터 구현은 첫 버전 범위에서 제외한다. 모델 파일이나 검색 태그 대신 실제 서버의 요청·응답 계약을 기준으로 연결 가능 여부를 판단한다.

## 2. 현재 프로젝트에 추가할 경계

현재 앱에는 채팅, 모델 실험실, 에이전트 실험, 결과 동기화 작업 공간이 있다. 모델 실험실의 생성형 응답 기록과 에이전트 실험의 행동 기록은 Decision 결과와 구조가 다르다.

- 모델 실험실 진입 후 `생성형 평가 / Decision Benchmark`를 선택하도록 한다. Decision 전용 최상위 메뉴는 추가하지 않는다.
- 연결 선택, 실행 기록 사이드바, 비교와 보고서의 사용 경험은 기존 기능을 따른다. Decision 전용 화면과 결과 타입은 별도로 둔다.
- 프런트엔드는 설정·진행·결과 표시를 담당한다. Go 백엔드가 HTTP 호출, 요청 취소, 데이터 검증, 채점, 저장을 소유한다.
- 기존 에이전트 평가의 백그라운드 순차 실행·이벤트·앱 종료 처리 패턴을 참고한다. 채팅 스트리밍 실행기를 Decision 요청에 그대로 사용하지 않는다.
- 내부 평가 데이터와 채점기는 서버 요청 형식에서 분리한다. 첫 연결 어댑터로 System One 하나를 구현하며, 미래의 비호환 모델을 위한 임의 매핑 편집기나 플러그인 시스템까지 만들지는 않는다.
- 첫 버전의 결과 이동은 보고서 내보내기·가져오기로 제공한다. 기존 PC 간 결과 동기화 프로토콜 확장은 후속 작업으로 둔다.

기존 연계 지점은 `frontend/src/ModelBenchmark.tsx`, `app.go`, `agentic_evaluation.go`다. 생성형 벤치마크 기록에 Decision 결과를 끼워 넣거나 기존 저장 형식을 일괄 변경하지 않는다.

## 3. 호출 방식과 현재 Laya 서버

### 3.1 확인된 서버 상태

사용자가 제공한 최신 동작 테스트에서 다음이 확인됐다.

| 항목 | 값 또는 확인 상태 |
|---|---|
| 서버 | DGX Spark · `laya-serve` |
| 가상환경 위치 | `/home/nurivoice/laya-multilingual/.venv` |
| 실행 설정 | `USE_TF=0`, `LAYA_DEVICE=cuda`, `LAYA_MODELS=multilingual`, `LAYA_PRELOAD=1` |
| 바인딩 | `LAYA_HOST=0.0.0.0`, `LAYA_PORT=12300` |
| 로컬 호출 | `http://127.0.0.1:12300/v1/systemone` 정상 응답 |
| 요청 모델 ID | `multilingual` |
| 반환 최상위 모델 | `laya-rl-agent` |
| 실제 라우팅 모델 | `routing.model = multilingual` |
| 입력 상태 | 테스트 응답에서 `truncated = false` |

이 결과는 DGX 내부 HTTP API의 정상 동작을 확인한 것이다. Mac에서 DGX 사설 IP로 같은 요청을 성공시키는 외부 연결 검증은 아직 남아 있다. 최신 운영 포트는 **12300**으로 기록한다. 초기 설치 문서의 12200과 혼동하지 않는다.

앱에는 `http://<DGX 사설 IP>:12300`을 기본 URL로 등록한다. `0.0.0.0`은 서버 바인딩 값이며 클라이언트 접속 주소가 아니다. 제공된 HTTP 응답만으로 GPU 사용 여부나 처리 시간이 검증됐다고 표시하지 않는다.

### 3.2 공통 요청·응답 계약

Go 백엔드에서 `POST /v1/systemone`으로 요청한다. Laya와 Ollama의 Decision API는 이 경로에서 typed decision을 제공한다. [Laya 서버 문서](https://github.com/NandhaKishorM/laya#self-hosting-http-server-jev-compatible), [Ollama Nimble API](https://ollama.com/library/nimble)

```json
{
  "model": "multilingual",
  "state": {"body": "평가할 입력 텍스트"},
  "questions": {
    "decision": {
      "type": "choice",
      "instructions": "버전이 고정된 판단 지시문",
      "criteria": {
        "label_a": "첫 번째 선택지의 기준",
        "label_b": "두 번째 선택지의 기준"
      }
    }
  }
}
```

- 대상마다 서버 URL과 모델 ID를 바꾼다. 같은 케이스의 입력, 지시문, 선택지 설명과 순서는 동일하게 유지한다.
- 초기 비교는 요청당 케이스 하나·질문 하나로 실행한다. 서버별 배치 최적화나 여러 질문을 묶은 처리량 시험은 별도 후속 평가로 둔다.
- 모델 ID는 사용자가 직접 입력한다. Laya에는 요청마다 `multilingual`을 명시해 Router의 자동 체크포인트 선택을 방지한다.
- 서버 프로필은 이름, 기본 URL, 런타임 종류와 실행 환경 메모를 저장한다. 선택적 Bearer 토큰은 실행 중 메모리에서만 사용하고 기록·보고서·프로필 파일에는 저장하지 않는다.
- `answers.decision`을 질문 유형에 따라 해석한다. `usage`, `routing`, `answer_confidence`, `action`, `x_jev_confidence` 등 확장 필드는 존재할 때 보관한다. 확장 필드가 없다는 이유로 정상 응답을 거부하지 않는다.
- 최상위 반환 모델명과 Laya의 `routing.model`을 따로 보관한다. 요청 모델과 실제 라우팅 모델이 다르면 해당 결과를 비교 적합성 경고로 표시한다.
- 연결 테스트는 작은 알려진 요청의 응답 구조를 확인하는 검사다. 그 요청의 정답 일치 여부를 전체 모델 성능으로 해석하지 않는다.

`noul`은 참일 확률, `score`는 등급별 확률과 확률 가중 평균 등급을 반환한다. 따라서 모든 응답에 `choice`나 `confidence`가 있다고 가정하지 않는다. [Ollama Decision 답변 형식](https://ollama.com/library/nimble)

## 4. 기본 데이터셋과 한국어·영어 구성

### 4.1 기본 세트 선정 기준

기본 세트의 실제 출처·이름·문항 수는 아직 선정되지 않았다. 아래 기준으로 공개 데이터셋을 조사하고, 선정표를 확정하는 것을 구현의 첫 단계로 둔다.

| 검토 항목 | 채택 조건 |
|---|---|
| 출처·사용 조건 | 원본 URL, 리비전, 평가 split, 라이선스와 앱 내 재배포·번역 가능 여부를 확인한다. |
| 정답 | 사람 검토 또는 검증 가능한 규칙 기반 정답을 우선한다. 모델 생성 정답은 검토 없이 확정하지 않는다. |
| 평가 독립성 | 평가 split을 사용하고, 알려진 학습 포함 여부와 정보가 없는 경우를 기록한다. |
| 한국어 품질 | 자연스러운 입력과 지시문, 모호하지 않은 선택지 기준을 검토한다. |
| 영어 대응 | 같은 의미와 판단 조건을 유지하는 대응 문항을 만들고 정답 유지 여부를 검토한다. |
| 클래스 구성 | 클래스별 문항 수를 공개하고 쉬운 다수 클래스만으로 높은 점수가 나오지 않게 구성한다. |
| 입력 길이 | 모델의 입력 한계를 검토하고, 긴 입력 과제는 짧은 입력 과제와 별도 세트로 관리한다. |
| 재현성 | 전체 데이터 또는 고정된 표본 ID·선정 규칙·seed를 보관한다. 실행할 때마다 표본을 바꾸지 않는다. |

후보 과제는 의도·주제 분류, 조건 충족·사실 관계의 이진 판단, 요약 충실도·답변 관련성 등의 등급 평가다. 이는 선정할 과제 종류이며 특정 공개 데이터셋이 채택됐다는 뜻은 아니다.

등급 평가는 순서가 있는 라벨에 대한 판단이다. 예를 들어 `무관함 / 일부 관련 / 직접 관련`의 기준을 모델에 주는 것이다. 앱이 모델에 부여하는 종합 평가 점수와 구분한다. 세 유형 모두 기본 구성에 포함하며, 정식 제공 전에 각 유형의 정답 기준과 검토 품질을 확보한다.

### 4.2 이중 언어 세트

- 기본 실행 언어는 한국어이며 `한국어 / 영어 / 둘 다`를 선택한다.
- 대응 문항에 공통 `pairID`를 부여하고, 언어별 케이스 ID는 별도로 유지한다.
- 지시문·선택지 설명·본문을 각 언어로 검토한다. 선택지의 내부 키는 동일하게 유지한다.
- 번역된 부정문·조건문·문화적 표현과 정답 유지 여부를 검토한다. 언어별 정답이 달라진 문항은 수정하거나 대응 비교 대상에서 제외한다.
- 한국어와 영어 결과를 각각 집계한다. 선택적으로 대응 문항의 예측 일치율과 한 언어에서만 틀린 사례를 표시한다. 예측 일치율은 정답률과 구분한다.
- 두 언어 점수를 무조건 합친 단일 순위는 기본으로 제공하지 않는다. 입력 언어와 지시문 언어의 교차 실험은 후속 범위로 둔다.

### 4.3 내부 데이터 계약과 편집

서버 요청 JSON 자체를 데이터셋의 원본 형식으로 삼지 않는다. 버전 있는 평가 계약을 저장하고 System One 어댑터가 요청으로 변환한다.

| 데이터 단위 | 주요 정보 |
|---|---|
| `DecisionSuite` | ID·버전·이름, 출처·리비전·split·라이선스, 표본 선정 정보, 검토 상태, 과제와 문항 목록 |
| `DecisionTask` | ID·버전, 유형, 언어별 지시문·선택지 또는 등급 설명, 순서, 채점 규칙 버전 |
| `DecisionCase` | ID, pairID, taskID, 언어, 입력 텍스트, 기대 라벨·참/거짓·등급 |

기본 세트는 읽기 전용으로 제공한다. 편집하려면 사용자 세트로 복제하며, 변경된 내용에 새 버전과 지문을 부여한다. 정답과 출처 메타데이터는 모델 요청에 보내지 않는다.

전체 세트는 JSON으로 가져오기·내보내기한다. 대량 케이스 편집에는 UTF-8 CSV를 제공하며 헤더는 `id,pair_id,task_id,language,text,expected`로 한다. CSV는 선택한 세트의 과제 정의를 참조한다. 단일 과제에서는 과제·언어를 화면에서 지정해 기본값으로 적용할 수 있게 한다.

CSV의 기대값은 choice의 선택지 키, noul의 `true` 또는 `false`, score의 0부터 시작하는 등급 번호다. BOM·따옴표·본문 줄바꿈을 지원하고, 중복 ID·미등록 과제·잘못된 언어·유형과 맞지 않는 정답을 행 번호와 함께 알려 준다. 검증 실패 시 일부 행만 자동으로 가져오지 않는다.

## 5. 채점과 비교 규칙

| 과제 | 정답 판정 | 주요 지표 |
|---|---|---|
| choice | 반환 선택지와 기대 라벨의 일치 | 정확도, 클래스별 precision/recall/F1, macro F1, 혼동행렬 |
| noul | `P(true) >= 0.5`를 참으로 판정 | 정확도, precision/recall/F1, 오탐률·누락률, 혼동행렬 |
| score | 확률이 가장 높은 등급과 기대 등급의 일치 | 최상위 등급 정확도, 최상위 등급 MAE, 기대 등급 점수 MAE |

확률이 같은 score 등급은 정의된 순서에서 첫 등급을 선택한다. 기대 등급 점수 MAE는 반환된 확률 가중 평균과 정답 등급 사이의 오차다. 최상위 등급 MAE와 이름을 구분한다. 이진 임계값과 tie 규칙은 채점 버전에 포함한다.

### 품질과 확률

- 정답률의 기본 분모는 유효한 응답을 얻은 문항 수다. 반드시 전체 문항 수·채점 가능 수·정답 수·실행 성공률을 함께 표시한다.
- 보조 지표로 전체 시도 문항 대비 정답 수를 제공한다. 연결 실패를 순수 판단 오류로 해석하지 않도록 별도 이름으로 표시한다.
- 모델 간 비교에서는 동일 문항에 대한 결과를 우선하고, 채점 가능 문항이 다르면 공통 문항 수와 누락·오류를 표시한다. 성공 문항만 달라진 평균을 조용히 동등 비교하지 않는다.
- 확률 품질은 Brier score와 ECE로 평가한다. choice는 전체 선택지, noul은 `[1-p, p]`, score는 등급 분포를 사용한다.
- 다중 클래스 Brier는 문항별 `sum((p_k - y_k)^2)`의 평균으로 정의한다. ECE는 최고 확률과 정답 일치 여부를 10개의 동일 너비 구간으로 묶어 계산한다. 정의와 표본 수를 보고서에 포함한다.
- 확률은 유한하고 0~1이어야 한다. choice/score는 정의된 키가 모두 있어야 하며, 합이 1에서 0.01 이내이면 반올림 오차로 보고 채점용 복사본만 정규화한다. 범위를 벗어나면 확률 지표를 평가 불가로 표시하고 원본과 사유를 남긴다.
- 라벨은 유효하지만 확률이 잘못된 경우 라벨 지표와 확률 지표의 채점 가능 수를 각각 표시한다. 확률을 임의로 추정하거나 confidence를 확률 분포로 대체하지 않는다.
- 표본이 적거나 한 클래스에 편중된 경우 표본 수와 분포를 함께 안내한다. 지표가 없는 경우 0점 대신 평가 불가로 표시한다.
- 서버의 `confidence` 정의가 다를 수 있으므로 원본 필드로 열람한다. 공통 임계값을 적용한 confidence 순위는 기본 비교에 사용하지 않는다.

### 시간과 비교 조건

- 모델·언어·과제별 측정 전에 준비 요청을 1회 수행한다. 준비 요청과 연결 검사 결과는 정답률·지연시간 집계에 넣지 않는다. 준비 요청 1회가 모든 입력 형태의 준비를 보장한다고 해석하지 않는다.
- 처리 시간은 Go에서 HTTP 요청 전송 시작부터 응답 본문 수신 완료까지 측정한다. 네트워크·서버 대기·추론이 포함된 왕복 시간이며, GPU 순수 추론 시간으로 표시하지 않는다.
- 정상 완료 요청의 평균·p50·p95·최소·최대와 표본 수를 제공한다. 오류·시간 초과의 경과 시간은 별도 보관한다. 백분위 계산은 정렬 후 nearest-rank를 사용한다.
- 속도 비교에는 하드웨어, 런타임·버전, 모델 태그·리비전, 양자화·정밀도, 실행 순서와 알려진 입력 제한을 함께 표시한다. 모르는 정보는 미확인으로 남긴다.
- 환경 메모가 같다는 이유만으로 자동으로 공정한 속도 순위를 보장하지 않는다. 환경과 측정 조건이 다르거나 미확인이면 참고값 비교로 표시한다.
- 서버가 보고한 truncation은 문항별로 표시한다. 잘린 응답의 결과는 진단용으로 남기되 기본 품질 비교의 채점 대상에서 제외하고 제외 수를 공개한다. 보고하지 않는 서버는 `잘림 여부 미확인`으로 남긴다.
- 최대 3개 기록 비교는 세트·과제·언어·문항 스냅샷과 채점 버전이 일치하는 경우에 제공한다. 한국어와 영어 간 대응 비교는 같은 pairID를 가진 별도 보기로 제공한다.
- 과제별·언어별 성능을 먼저 보여 준다. 데이터 크기가 다른 과제의 값을 합쳐 하나의 범용 성능 점수를 만들지 않는다.

## 6. 실행 흐름과 공개 인터페이스

실행 순서는 `세트·언어 선택 → 대상 서버·모델 선택 → 조건 검증 → 스냅샷 저장 → 준비 요청 → 순차 호출·채점·저장 → 결과 비교`다. 사용자는 선택한 여러 대상에 동일 세트를 한 번의 대기열로 실행할 수 있다.

- 한 번에 요청 하나만 실행한다. 대상 → 과제 → 언어 → 케이스 순서를 고정하고 실제 순서를 기록한다.
- 기본은 케이스당 1회 실행이다. 품질 결과에 정답을 얻을 때까지 재시도하는 방식을 넣지 않는다.
- 측정 요청의 자동 재시도는 하지 않는다. 재실행은 새 기록으로 남겨 오류와 재시도 성공을 숨기지 않는다.
- 표준 요청 시간 제한은 60초, 느린 서버 프리셋은 180초로 제안한다. 준비 요청도 선택한 제한을 적용한다. 이 값은 UI와 기록에 명시하고 비스트리밍 요청에 맞는 절대 제한을 사용한다.
- 문항 오류는 사유를 저장하고 다음 문항을 진행한다. 연결 검사·준비 단계에서 대상이 실행 불가능하면 그 대상은 실패로 끝내고 다음 대상으로 이동한다.
- 취소하면 진행 중 요청을 취소하고 남은 문항을 실행하지 않는다. 이미 완료된 문항은 보존한다. 앱 재시작 시 실행 중 기록은 중단 상태로 마감하며 자동 재개하지 않는다.
- 문항마다 저장한 뒤 진행 이벤트를 보낸다. 저장 실패 시 실행을 중단하고 오류를 전달한다. 실행 중 화면 전환·삭제 규칙은 기존 평가 기능과 일관되게 적용한다.

공개 타입은 `DecisionTarget`, `DecisionSuite`, `DecisionTask`, `DecisionCase`, `DecisionBenchmark`, `DecisionCaseResult`, `DecisionBenchmarkSummary`, `DecisionBenchmarkEvent`를 중심으로 설계한다. 타입은 다음 책임을 가진다.

| 인터페이스 그룹 | 제공 기능 |
|---|---|
| 대상 설정 | System One 서버 프로필 목록·저장·삭제, 실행 중 토큰 전달, 모델 ID와 알려진 실행 환경 입력 |
| 데이터셋 | 기본·사용자 세트 목록·열기, 사용자 세트 저장·복제·삭제, JSON 세트·CSV 케이스 입출력 |
| 실행 | 연결 검사, `StartDecisionBenchmark`, `CancelDecisionBenchmark`, 현재 실행 조회 |
| 기록 | `ListDecisionBenchmarks`, `OpenDecisionBenchmark`, `DeleteDecisionBenchmark` |
| 보고서 | Decision 보고서 저장·가져오기, 중복 기록 판정 |
| 이벤트 | `decision-benchmark:event`: 시작, 준비, 문항 완료·오류, 진행률, 취소, 완료·실패 |

`StartDecisionBenchmark`는 세트 스냅샷, 언어 선택, 대상 목록과 실행 규칙을 받고 생성한 기록을 반환한다. `DecisionCaseResult`에는 문항·대상 식별자, 상태, 정답·판단, 확률, 채점 결과, 시작·종료·왕복 시간, usage와 서버 메타데이터를 담는다. Wails 바인딩과 이벤트 타입은 Go 정의에서 다시 생성한다.

## 7. 화면·저장·보고서

설정 화면은 대상 서버와 모델, 기본·사용자 세트, 한국어·영어·둘 다, 과제와 문항 수, 예상 요청 수를 보여 준다. 세트의 출처·검토 상태·버전과 입력 길이 제약을 실행 전에 확인할 수 있게 한다.

결과 화면에는 과제별·언어별 지표, 실행 성공률, 오류 유형, 혼동행렬, 확률 품질, 시간 분포를 표시한다. 문항 상세에는 입력·판단 기준·정답·모델 판단·전체 확률·원본 응답을 제공한다. 틀린 문항, 실행 오류, 잘린 입력, 한국어·영어 판단 불일치를 필터링할 수 있게 한다.

- 세트와 Decision 기록은 앱 데이터 루트의 독립 저장 영역으로 관리한다. 기존 생성형·에이전트 기록의 읽기 형식을 변경하지 않는다.
- 기록에는 스키마·채점 버전, 세트 내용과 지문, 모델·환경 스냅샷, 준비 요청과 문항별 결과를 보관한다.
- Markdown 기록과 복원 가능한 구조화 메타데이터를 사용해 기존 저장 경험을 따른다. 원자적 저장, 안전한 ID 검사, 기록 크기 검사를 적용한다.
- 보존 기본값은 최근 종료 기록 80개, 단일 기록 최대 64MiB로 제안한다. 실행 중 기록은 정리·삭제 대상에서 제외하고, 새 실행 전 보존 한도를 확인한다.
- 보고서는 단일 기록과 최대 3개 비교를 Markdown/HTML로 내보낸다. 세트 출처·버전·언어, 실행 환경, 지표 정의·분모, 오류·제외 수를 포함한다.
- 복원용 원본 데이터를 보고서에 포함하고, 가져올 때 버전·내용 검증과 지문 기반 중복 검사를 수행한다. 가져온 기록은 원본을 수정하지 않는다.
- 입력·선택지·서버 오류 등 외부 문자열은 HTML 출력 시 이스케이프한다. 인증 토큰과 인증 헤더는 어떤 기록에도 넣지 않는다.

## 8. 구현 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| A. 기본 세트 확정 | 공개 데이터 조사, 라이선스·정답·번역 검토, 과제·채점 규칙·버전 확정 | 세 유형 모두 출처·문항 ID·한국어/영어 대응·정답 검토 상태가 있는 선정표와 고정 세트가 준비된다. |
| B. 평가 계약·채점 | 세트·과제·문항·결과 타입, JSON/CSV 검증, 각 유형 지표·비교 지문 구현 | 알려진 정답·예측·확률의 고정 입력으로 계산 결과가 검증된다. |
| C. 서버 연결·실행 | System One 어댑터, Laya·Ollama 연결 검사, 순차 대기열·취소·이벤트·기록 구현 | 동일 세트를 두 대상에 실행하고 완료·오류·취소 기록을 정확히 남긴다. |
| D. 실험실 화면 | 평가 종류 선택, 대상·세트·언어 설정, 사용자 편집·가져오기, 실행·상세 결과 | 한국어 기본 실행과 영어/둘 다 실행을 UI에서 사용할 수 있다. |
| E. 비교·보고서 | 최대 3개 비교, 대응 언어 비교, Markdown/HTML 왕복 | 동일 조건 비교와 다른 조건 경고, 보고서 복원이 검증된다. |
| F. 통합 확인 | Mac→DGX 사설망 연결, 실제 Laya와 Nimble 실행, 기존 기능 회귀 확인 | 실제 환경에서 두 모델의 과제별·언어별 결과를 저장·비교·내보내기 한다. |

A 단계의 실제 데이터셋 선정은 별도 구현 작업이며, 이 문서를 생성한 시점에는 완료되지 않았다. 문항 수는 데이터 품질·표본 구성·실행 비용 검토 뒤 선정표에서 확정한다. 프로토콜 테스트용 문항은 구현 검증에 사용할 수 있지만 정식 기본 벤치마크로 표시하지 않는다.

## 9. 검증 계획

### Go 단위·통합 테스트

- 사용자가 제공한 Laya 응답을 fixture로 사용해 최상위 모델명과 routing 모델명, 추가 필드, 잘림 정보를 검증한다.
- Ollama와 동일 기본 계약의 모사 서버로 choice/noul/score를 모두 검증한다. noul의 confidence 부재를 정상 처리한다.
- HTTP 오류, 비JSON 응답, 누락 질문, 미등록 선택지, NaN·범위 밖 확률, 잘못된 확률 합, 잘린 입력을 검증한다.
- 타입별 정답 판정, macro F1, 오탐·누락, 두 종류의 등급 MAE, Brier·ECE와 시간 백분위를 고정 수치로 검증한다.
- 오류·취소·채점 가능 수·확률 평가 가능 수가 각 지표의 분모에 올바르게 반영되는지 확인한다.
- CSV의 한국어·영어, 줄바꿈·따옴표·BOM, 잘못된 기대값·ID·pairID를 검증한다.
- 시간 초과·진행 중 취소·종료 후 재시작·저장 실패, 보고서 왕복·중복·과거 버전 검사를 확인한다.

### 화면·실제 환경 확인

- 한국어 기본값과 영어·둘 다 선택, 기본 세트 복제·편집·가져오기, 실행 중 진행률·취소를 확인한다.
- 과제별·언어별 결과, 오류·평가 불가·잘림 표시, 원본 상세, 대응 문항 필터를 확인한다.
- 다른 세트·채점 버전의 비교 차단과 환경이 다른 시간 비교 안내를 확인한다.
- Mac에서 `http://<DGX IP>:12300/v1/systemone` 호출 성공을 확인한다. DGX 로컬 호출 성공으로 대체하지 않는다.
- 동일한 고정 세트를 Laya Multilingual과 Ollama Nimble에 실행한다. 특정 모델이 더 높은 점수를 받는 것을 완료 조건으로 삼지 않는다.
- 변경에 해당하는 Go 테스트와 프런트엔드 테스트·빌드를 실행하고, 채팅·기존 모델 실험실·에이전트 실험·결과 동기화 진입에 회귀가 없는지 확인한다.

## 10. 아직 남은 결정과 참고 자료

### 구현 전 확정할 항목

1. 기본 데이터셋의 실제 이름·출처·split·리비전·라이선스·표본 수와 문항 ID
2. 세 유형의 한국어·영어 대응 문항과 지시문·선택지 또는 등급 설명의 검토 결과
3. Mac에서 접근할 DGX 사설 IP와 비교할 Ollama 서버 주소·실제 모델 태그

시간 제한, 저장 상한과 세부 CSV 형식 등 이 문서의 **제안 기본값**은 구현 검토 기준이다. 합의된 제품 방향과 달리 이미 검증된 운영 설정으로 표시하지 않는다.
