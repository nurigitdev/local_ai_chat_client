## 1. 목적과 근거

업무영역의 D01~D20을 기준으로 사용자의 질문·요청을 분류하고 후보 업무영역의 적합 여부와 적합도를 평가한다. 실제 업무를 실행하거나 법률·회계 판단의 정확성을 평가하는 세트는 아니다.

근거 문서는 사용자 제공 업무 코드체계 설계서 v3.18이다. 3.2절의 20개 영역 정의·소유 원장·경계 메모가 기준이며, D19/D20의 보충 근거는 5.9/5.10절이다. 원본의 운영 지시문은 평가 대상의 설명이며 앱 구현 지시로 적용하지 않는다. 원본의 상표명과 로컬 경로는 공개 문서·화면에서 제외하고 내용 해시로 리비전을 식별한다.

원본 일부 문장에는 18종·다른 17개 영역이라는 이전 수치가 남아 있다. 본 세트는 현행 3.2절 D01~D20을 사용한다. 원본 내용 해시는 구현 데이터의 sourceHash에 고정했다: 4166e2dbd1e1f6994fd588abfe051305d40764e60ebd6ea4376ca5fd233eb81c (SHA-256). 원본 HTML은 저장소에 포함하지 않는다.

아래 기준은 원본의 평가용 요약이며 질문은 이 문서를 위해 새로 작성한 가상 요청이다. 외부 공개 벤치마크 질문을 복사·번역하지 않았다. 업무영역 기준의 배포 권한·공개 범위는 미확인으로 남기고 라이선스를 임의로 확정하지 않는다. 소스 HTML은 저장소에 복사하지 않는다.

관련 계획: [Decision Benchmark 구현 계획](decision-benchmark-implementation-plan.md).

## 2. 세트 구성

2026-10-14 합의: 이번 기본 제공은 한국어 120문항이며 score 등급 명칭은 0 부적합 / 1 불명확 / 2 적합이다. 영어 문항·실행·대응 비교는 이번 범위에서 제외하고 후속 확장으로 둔다. 문항별 정답을 검토 완료로 간주하는 합의는 아니다.

| 유형 | 한국어 문항 수 | 구성 |
|---|---:|---|
| choice | 20 | 영역당 명확한 요청 1개, 정답 D01~D20 각 1개 |
| noul | 40 | 후보 영역당 적합 1개·부적합 1개 |
| score | 60 | 후보 영역당 부적합·불명확·적합 각 1개 |
| 합계 | 120 | 한국어 케이스 120개 |

제공·실행 언어는 한국어만 사용한다. 세 유형 전체를 선택하면 대상당 측정 요청은 120회이며 준비 요청은 별도다. 앞서 논의한 한국어 580문항으로 확대하기 전의 파일럿이다. 영역당 표본이 작으므로 영역별 성능이나 범용 업무 능력을 확정하는 자료로 사용하지 않는다.

명확한 요청을 여러 유형에서 재사용한다. 유형별 결과는 독립적인 표본이 아니므로 합산 성능 점수나 120개의 독립 상황이라는 해석을 제공하지 않는다. 자체 평가 전용 세트이며 학습 split은 없다. 프롬프트 개발에 사용한 문항은 향후 별도 평가 세트에서 제외한다.

## 3. 공통 판단 원칙

1. 등장하는 부서·단어보다 요청의 핵심 작업과 산출물을 본다.
2. 원장·형상·기록의 소유 경계를 구분한다.
3. 프로젝트 내 개발·구매 작업을 모두 D12로 분류하지 않는다. D12는 집합 관리다.
4. 신청·심의·개설 본체는 D12다. 착수 전이라는 이유만으로 D19가 되지 않는다.
5. 전문 내용의 작성과 지식 등재·색인을 구분한다. 등재·색인 관리가 D20이다.
6. 총무 D13을 나머지 모든 요청의 기본값으로 사용하지 않는다.
7. choice/noul에는 단일 핵심 작업이 명확한 요청만 사용한다. 모호한 요청은 score 1등급으로 사용한다.
8. 업무 외 질문·동등한 복합 작업·자동 되물음은 후속 과제다. 현재 choice에는 기타/확인필요 라벨이 없다.

## 4. 모델에 제공할 영역 기준

아래 표는 영역 정의의 공통 근거다. 실행에는 다음 두 질문 구성을 제공한다. 한 실행의 모든 모델에는 동일한 구성을 적용하며 서버별로 자동 축약하거나 재시도하지 않는다.

- **간결한 질문 (기본)**: choice에는 짧은 지시문과 20개 선택지별 업무 정의를 전달한다. noul/score에는 후보 업무 정의를 문항별 판단 질문에 넣고 입력 본문은 실제 요청만 전달한다. 정답·정답 근거는 요청에 추가하지 않는다.
- **상세한 기준**: 기존과 같이 모든 영역의 정의와 경계를 지시문과 선택지에 전달한다. 긴 기준 입력을 지원하는 서버에서 선택한다.

choice의 간결한 선택지는 D01~D20 순서로 회로기구 설계, 펌웨어 구현, SW 개발배포, 회계 기록결산, 자금 계획조달, 제품 생산, 채용근태 평가, 급여공제 계산, 설계 검증인증, 양산 검사판정, 제품 고객출하, 프로젝트 관리, 공통 자산계약, 고객 견적수주, 부품 발주입고, 창고 수불인계, 보도IR 소통, 독립 감사시정, 아이디어 조사, 지식 등재색인다. 0.5부터 state.body에는 실제 요청만 전달한다. 후보별 질문은 cases[].instructions.ko에 저장하며 questions.decision.instructions로 보낸다. 이전 0.4의 공통 설명 본문 결합은 폐기했다. 간결형은 상세형의 전체 경계 설명과 정보량이 다르므로 두 구성의 결과를 동일 조건으로 비교하지 않는다.

간결형 지시문은 choice `이 요청을 담당할 업무를 고르세요.`, noul `요청의 핵심 작업이 후보 기준에 해당합니까?`, score `후보 기준에 대한 요청의 적합도를 평가하세요. 정보가 부족하면 불명확입니다.`를 사용한다. 실제 실행 파일은 각각 `frontend/src/datasets/domainDecisionSuite.json`과 `domainDecisionSuiteDetailed.json`이다. 아래 유형별 긴 지시문은 상세형의 기준이다.

## 5. 유형별 질문·정답 기준

### 5.1 choice — 업무영역 분류

과제 ID: business-domain-choice

한국어 지시문: 업무영역 기준에 따라 요청의 핵심 작업과 산출물을 담당하는 영역 하나를 선택하세요. 단순히 등장하는 단어나 프로젝트 소속으로 분류하지 마세요.

선택지는 4절 D01~D20, 고정 순서다. 정답은 영역 키다. 유효한 반환 라벨과 정답이 같으면 맞음이다. 미등록 키는 응답 오류다. 확률은 20개 라벨 모두를 대상으로 검증한다.

### 5.2 noul — 후보 영역 적합 여부

과제 ID: business-domain-membership

한국어 지시문: 후보 업무영역의 기준에 요청의 핵심 작업이 해당하면 참, 명확하게 다른 영역의 작업이면 거짓으로 판단하세요.

false 기준: 핵심 작업이 후보가 아닌 다른 영역에 명확히 속함.<br>
true 기준: 핵심 작업이 후보 영역에 명확히 속함.

후보 업무 정의는 문항별 질문에 표시하고 본문에는 요청만 전달한다. 모호한 요청을 거짓으로 간주하는 과제가 아니므로 모호한 요청은 넣지 않는다. 기대값은 의미상 boolean이다. P(true) >= 0.5이면 참, 그 미만이면 거짓으로 판정한다. confidence 필드가 없어도 정상이다.

### 5.3 score — 후보 영역 적합도

과제 ID: business-domain-fit

한국어 지시문: 요청의 핵심 작업이 후보 업무영역에 얼마나 명확히 해당하는지 아래 0·1·2등급 기준으로 평가하세요. 실행 가능성, 위험도, 요청의 상세함 전체 또는 모델 자신의 확신도를 점수로 매기지 마세요.

| 등급 | 한국어 기준 |
| --- | --- |
| 0 | 부적합: 핵심 작업이 다른 영역에 명확히 속하고 후보 영역의 작업은 요청하지 않음 |
| 1 | 불명확: 후보와 관련된 주제이지만 작업·산출물이 특정되지 않아 영역을 확정할 수 없음 |
| 2 | 적합: 핵심 작업·산출물이 후보 영역의 정의와 경계에 명확히 해당함 |

이 등급은 원본의 기존 점수가 아니라 사용자가 채택한 본 벤치마크의 평가 기준이다. 복합 요청의 부분 적합은 이번 초안에 포함하지 않는다. 날짜·수량·담당자가 없어도 영역이 명확하면 2등급일 수 있다. 예: 급여를 계산해 달라는 요청은 직원 명단이 없다는 이유만으로 1등급이 되지 않는다.

최대 확률의 등급을 예측 등급으로 택하고, 동률이면 0→1→2 순서에서 먼저 등장한 등급을 택한다. 확률 가중 평균 등급은 sum(k × p[k])다.

## 6. 문항 ID·입력·검토 정보

아래 표의 문항 기준 ID를 바탕으로 case ID는 -ko를 붙인다. language는 ko다. 향후 대응 언어 확장을 위해 pairID에는 문항 기준 ID를 보관하되 현재 영어 케이스는 생성하지 않는다.

- C-Dxx-01: 명확한 원안 요청 → choice.
- N-Dxx-T01: 같은 영역 원안 + 후보 → noul true.
- N-Dxx-F01: 다른 영역 원안 + 후보 → noul false.
- S-Dxx-0/1/2: 다른 영역 원안/모호한 요청/같은 영역 원안 + 후보 → score.
- A-Dxx는 명확한 원안, U-Dxx는 모호한 요청의 scenarioID다. 유형 간 재사용 관계를 기록한다.

전 문항 sourceSection은 업무영역 v3.18 §3.2다. D19/D20은 §5.9/§5.10도 기록한다. 개별 업무코드는 이번 영역 평가에서 미지정이다. 원본 8절과 대조한 경우에만 verifiedWorkCode를 채우며 코드를 추정하지 않는다.

전 문항 reviewStatus=unreviewed, 정답 상태=proposed다. 번역 검토는 이번 범위에 해당하지 않는다. 표의 근거는 정답 제안이지 사람 검토 완료 표시가 아니다.

모델 본문 형식:

~~~text
choice:
요청: {한국어 요청}

noul/score:
후보 업무영역: {Dxx} — {업무영역 이름}
요청: {한국어 요청}
~~~

noul/score의 지시문에도 4절의 전체 영역 기준을 제공한다. 후보는 판단 대상 문맥이다. 후보마다 별도 과제를 만들지 않고 과제는 세 개로 구성한다. 표의 후보·요청을 위 본문으로 조합해 state.body로 보낸다. 정답·근거·case ID·pairID·scenarioID는 보내지 않는다. T/F나 등급을 나타내는 ID는 모델 입력에 포함하지 않는다.

## 10. 채점·집계 규칙

| 유형 | 라벨 지표 | 확률 지표 |
|---|---|---|
| choice | 정확도, 영역별 precision/recall/F1, macro F1, 20×20 혼동행렬 | 20개 영역 분포의 Brier score, ECE |
| noul | 정확도, true를 양성으로 한 precision/recall/F1, 오탐률 FP/(FP+TN), 누락률 FN/(FN+TP), 혼동행렬 | [1-p, p] 분포의 Brier score, ECE |
| score | 최상위 등급 정확도, 최상위 등급 MAE, 기대 등급 점수 MAE, 3×3 혼동행렬 | 3등급 분포의 Brier score, ECE |

- 기대 등급 점수 MAE = mean(abs(sum(k × p[k]) - expected)). 최상위 등급 MAE = mean(abs(argmax(p) - expected)). 등급은 0~2다.
- Brier = mean(sum((p[k]-y[k])²)). ECE는 최고 확률과 그 클래스의 정답 여부를 10개 동일 너비 구간으로 집계한다. 구간은 [0,0.1), …, [0.9,1]이다. 빈 구간의 가중치는 0이다. noul도 최고 확률 클래스 기준이고 동률 예측은 true다.
- 확률은 유한한 0~1 값이어야 한다. choice/score는 정의된 모든 키가 필요하다. 합이 1에서 0.01 이내면 채점용 복사본만 정규화한다. 초과하면 확률 채점 불가 사유를 남긴다. 원본을 수정하지 않는다.
- choice는 유효한 반환 라벨이 있으면 확률 오류와 별개로 라벨 채점한다. noul은 유효한 P(true)가 없으면 라벨도 채점 불가다. score는 등급 도출에 유효한 분포가 필요하므로 잘못된 분포이면 라벨·확률 모두 채점 불가다. 다른 유형의 유사 필드를 임의로 대신 사용하지 않는다.
- 정답률의 기본 분모는 잘리지 않은 채점 가능 응답 수다. 전체 시도·HTTP 정상 완료·라벨 채점 가능·확률 채점 가능·정답·잘림 제외·오류 수를 함께 표시한다. 실행 성공률(HTTP 정상 완료 수/전체 시도 수)과 전체 시도 대비 정답 비율을 별도 표시한다.
- 지표의 분모가 0이면 0점 대신 평가 불가다. 일부 실패 시 모델 간 공통 채점 가능 문항의 성능도 표시한다.
- 한국어 결과를 유형별로 집계한다. noul/score는 후보별 분포도 표시한다. 유형을 합친 종합 순위는 제공하지 않는다.
- 영어 대응 비교와 언어별 예측 일치율은 후속 언어 확장 시 구현한다. 이번 결과 화면에 제공하지 않는다.
- HTTP 왕복 시간, 준비 요청, 취소와 오류 처리 규칙은 기존 구현 계획 5~7절을 따른다. 왕복 시간은 GPU 순수 추론 시간이 아니다.

## 11. 구현 계약으로 옮기는 방법

현재 프런트엔드 decision-benchmark-suite JSON v1은 설정 초안 형식이다. 문서 버전·세트 버전과 혼동하지 않는다. 한국어 기본 JSON과 Go 실행·채점·기록·보고서 구현을 연결했다. 기본 데이터는 frontend/src/datasets/domainDecisionSuite.json이며 Go에서 같은 파일을 임베드한다. 실제 서버 확인과 문항 정답 검토는 남아 있다.

세 과제를 각각 choice/noul/score로 만든다. 기본 세트 생성 시 language=ko인 120문항만 포함한다. 기존 GUI 타입이 ko/en 필드를 요구하는 제약은 변환·타입 정비 과정에서 처리하며, 이를 이유로 영어 문항을 기본 세트에 추가하지 않는다. 영어/둘 다 실행 선택은 이 세트에서 비활성화하거나 숨긴다. choice 옵션은 D01~D20, noul 옵션은 false/true, score 옵션은 0/1/2 순서다. 현재 GUI의 expected는 문자열이므로 noul은 true/false 문자열, score는 0/1/2 문자열로 기록한다. 최종 백엔드 계약에서 boolean/정수로 바뀌면 명시적 변환 경로를 둔다.

각 과제의 한국어 instructions에 4절 전체 영역 기준과 5절 지시문을 넣는다. choice criteria에는 한국어 영역 기준, noul criteria에는 false/true 설명, score criteria에는 순서가 있는 3등급 설명을 넣는다. 실제 요청·응답 계약은 어댑터 테스트로 검증한다.

출처·검토·scenarioID 같은 필드를 현재 GUI JSON에 추가하면 보존된다고 가정하지 않는다. GUI 가져오기는 정의된 ID·리비전·출처·원본 해시·채점 버전과 문항의 scenarioID·근거·후보 정보만 복원한다. 가져온 검토 상태는 unreviewed로 초기화하며 임의 필드를 보존하지 않는다.

구현된 기록에는 schema/scoring version, suite ID/revision, 원본 출처·해시, 지시문·선택지 순서, 정답·근거·검토 상태, pairID/scenarioID, 모델·환경 스냅샷을 포함한다. 사람 검토 이력의 입력·관리 기능은 후속이다. 다른 스냅샷 지문의 기록을 동일 조건으로 비교하지 않는다. 인증 토큰은 기록에 저장하지 않는다.

## 12. 정식 기본 세트 확정 조건

1. 업무 소관 검토자가 영역 기준과 모든 제안 정답을 검토한다. 특히 회계/재무, 인사/급여, 개발/양산품질, 구매/창고/제조/출하, D12/D19, 소관 내용 작성/D20 등재 경계를 확인한다.
2. score 1등급의 후보 관련성과 불명확성을 검토한다. 실제로 영역을 확정할 수 있는 요청이면 수정한다. 이견이 해결되지 않으면 제외한다.
3. 한국어 문항의 자연스러움, 작업·시점·부정·산출물과 정답의 일관성을 사람이 검토한다. 모델의 채점만으로 검토 완료 처리하지 않는다.
4. 검토자·날짜·변경 사유를 남기고 수정 시 새 버전으로 기록한다. 모델 출력에 맞춰 정답을 바꾸지 않는다.
5. 모델 입력과 정답·근거 메타데이터를 분리하고 ID의 T/F·등급 표식이 입력에 포함되지 않는지 확인한다.
6. 중복 ID, 한국어 외 케이스 포함, 미등록 후보, 잘못된 정답, 옵션·등급 순서, 유형별 분포를 검증한다.
7. 업무영역 기준의 앱 내 포함·배포 범위를 확인하고 최종 출처·라이선스 표시를 결정한다.

## 13. 후속 확장

검토 후 choice 영역당 10개(200), noul 영역당 true/false 각 5개(200), score 영역당 등급별 3개(180)의 한국어 580문항으로 확대할 수 있다. 영어 대응 세트는 별도 후속 합의가 있을 때 추가한다. 확장 문항은 아직 작성되지 않았고 영어 문항·기준은 이번 제공 문서에서 제외했다.

확장 시 자연스러운 질문 표현·다양한 작업·경계 사례를 추가한다. 템플릿의 숫자만 바꿔 표본을 늘리지 않는다. 복합 업무·업무 외 요청·필수 정보 부족·세부 업무코드 분류는 별도 과제로 설계한다. 실제 실행 라우팅·자동 승인 연결은 이번 벤치마크 범위에 포함하지 않는다.



## 11. 준비 실패와 결과 표시

연결 테스트는 세트와 무관한 짧은 예/아니요 요청으로 기본 API 응답만 확인한다. 실행 준비는 모델·평가 유형마다 첫 문항을 사용하며 측정 집계에서 제외한다. 준비 실패 시 해당 유형의 문항만 미실행으로 남기고 다른 유형과 다음 모델은 계속 진행한다. 미실행 문항을 오답으로 표시하지 않는다.

결과 화면은 모델별 전체·완료·오류·미실행 건수와 준비 실패 원인을 우선 표시한다. 유형별 정확도와 평균 응답 시간은 간단한 표로 제공하고 확률 지표·혼동행렬은 펼쳐 확인한다. 문항 상세는 모델·유형·결과로 필터링하며 한 페이지에 최대 20건을 표시한다. 기존 기록의 요청·정답 스냅샷은 변경하지 않는다.


## 12. 공통 업무 설명 보완 (0.4 간결형)

선택지 이름만으로 업무 분류를 판단하던 0.3 간결형은 3.2절의 한 줄 정의를 제공하지 않았다. 0.4 간결형은 모든 choice 문항에 같은 20개 영역 요약을 전달한다. 정의는 핵심 작업 위주로 요약하고, D19의 신청·개설은 D12 소유라는 경계와 D20의 내용 작성은 소관 영역이라는 경계를 포함한다. noul/score는 기존처럼 해당 후보 기준을 본문에 포함한다. 문항 ID·정답·근거는 유지하며 공통 설명 변경은 비교 지문에 반영한다. 이전 실행 기록은 수정하지 않는다.

입력 설명을 별도로 전달해도 서버의 전체 입력 길이 제한은 적용된다. 업무 설명 보완이 정확도를 얼마나 바꾸는지는 실제 모델 재평가로 확인해야 하며 현재 결과에서 오답 원인을 설명 부족 하나로 확정하지 않는다.


## 13. 현재 요청 구성 (0.5)

- state.body: 실제 요청만 전달한다. 후보 이름, 정의 목록, 정답과 근거를 넣지 않는다.
- choice.criteria: 선택지별 짧은 업무 정의(예: 회계 기록결산, 자금 계획조달)를 제공한다.
- noul/score.instructions: 후보 업무를 구체적으로 묻는다. 예: 회계 기록·결산 업무에 해당하는 요청인가요?
- 문항별 instructions는 JSON과 CSV instructions 열, 화면 편집, 요청 미리보기, 실행 기록과 HTML 보고서에 보존한다. 생략하면 공통 과제 지시문을 사용한다.
- 기존 업무 ID·정답은 유지하고 세트 버전과 비교 지문은 변경한다. 이전 실행 기록과 사용자 편집 세트는 덮어쓰지 않는다.

0.4 구성과 그 실행 진단은 변경 이력이다. 현재 기본 요청에서는 모든 업무 정의를 본문에 합치지 않는다.

### 공개 가상 문항 서버 확인

사용자의 업무 세트 대신 동물 20종 분류와 가상의 앱 오류·영수증 요청으로 두 서버를 확인했다. 모든 요청은 200 응답이었고 별도 서버는 입력 잘림 없음·누락 토큰 0을 보고했다. 두 모델 모두 고양이는 맞혔지만 개는 소로 잘못 판단했고, 부정 예/아니요 사례에도 높은 true 확률을 반환했다. 부정 기준을 구체적으로 바꾸면 score의 선택은 적합에서 불명확으로 달라졌으나 정답인 부적합까지는 구분하지 못했다. 이는 새 구성이 정답률 개선으로 검증됐다는 뜻이 아니다. 실제 120문항 성능과 해당 체크포인트의 한국어 판단 적합성 검증은 별도로 남는다.
